Team reference

PaperMind: AI-Powered Exam Grading

A web application that reads handwritten exam answer sheets and grades them against a typed answer key, using AI models that run entirely on the teacher's own computer. The teacher stays in charge: every uncertain mark is sent back for review.

Written for the team so everyone can understand the project we inherited, how it works inside, and how to run, explain and extend it. Repository: github.com/samyy2323/papermind-exam-grading

1The project in 2 minutes

The problem. Descriptive exam answers are slow and tiring to mark. A teacher reads every page of every script, compares it with a marking scheme, and decides partial marks. The same answer can get different marks at different times of day.

What we built. A teacher signs in, creates an exam, uploads the typed answer key, and then uploads each student's handwritten sheet as photos or a PDF. The system reads the handwriting, grades every question against the key, and shows each mark with a confidence value and a one-line reason. Anything doubtful goes to a review queue where the teacher accepts or overrides the mark. Results and class analytics are shown on a dashboard.

2

AI models, both local: Qwen2.5-VL (reads handwriting) and Llama 3 (grades).

0

Cloud calls and fees. Student scripts never leave the teacher's computer.

35

Questions in the test paper we used (20 MCQ at 1 mark, 15 short answers at 2 marks).

~15 min

Per 6-page sheet on a laptop with no graphics card: about 12 minutes reading the handwriting and 3 minutes grading.

The one-sentence version

Photos or PDF of a handwritten sheet go in; a vision model turns them into text; a language model marks each answer against the teacher's answer key; the teacher reviews the doubtful ones and gets final marks and analytics.

The three ideas to remember

  1. Two models, two jobs. One model only reads (image to text); another only judges (text to marks). Each does what it is good at.
  2. Local first. Everything runs through Ollama on the teacher's machine. That is the privacy and cost story.
  3. Teacher in the loop. The AI never has the last word on an answer it is unsure about. This is what makes it usable in a real examination.

4Architecture

Four layers, from what the teacher sees down to the models:

How the layers talk

  • The browser only ever talks to the Vite dev server. Vite forwards every URL starting with /api to the back end (vite.config.js proxy), so there are no cross-origin problems.
  • The back end never makes the browser wait for the AI. An upload saves the files, creates a submission row, starts a background task and answers immediately; the browser polls the status every 3 seconds.
  • Only grader.py talks to the models, through utils/ollama_client.py, which POSTs to Ollama's /api/generate.

5End-to-end workflow

This is the whole life of one exam, in the order it happens. The coloured tags show who does the work.

Teacher acts in the app · Browser front end · Server FastAPI · Model Ollama

  1. Create an account and sign in

    Teacher fills the sign-up form. Server checks name, email format and a 6-character minimum password, stores a salted hash, and returns a signed token. Browser keeps the token in localStorage and sends it on every request.

  2. Create the exam

    Teacher enters title, subject, sub-domain, total marks and number of questions. Server creates the exam as a draft and links it to a class for that teacher and sub-domain (the roster lives on the class).

  3. Upload the answer key

    Teacher uploads a typed PDF. Server reads its text and finds numbered entries (1. answer); if that fails it asks Llama 3 to structure it. It returns the questions without saving them. The page then shows the real PDF next to the extracted questions.

  4. Check and fix the questions

    Teacher edits question text, type (objective or subjective), reference answer and marks. Marks must add up to the exam total before publishing is allowed. Server saves the list.

  5. Publish

    Publishing validates the marks total and locks the questions, so every student is graded against the same paper.

  6. Add students and upload a sheet

    Teacher adds the student to the class roster and drops the sheet: photos, a PDF, or both. Server saves the files, renders any PDF pages to images, and builds one combined PDF (sheet.pdf) for the teacher to review later. It creates a submission and queues grading.

  7. Read the handwriting

    Server unloads Llama 3 from memory, then Qwen2.5-VL receives all page images (each shrunk to at most 768 px) and returns the written text with question numbers.

  8. Grade the answers

    Server unloads Qwen, then Multiple-choice questions are marked in code by comparing the chosen letter with the key. Llama 3 grades only the descriptive questions, in batches of eight, each seeing just its own answer. It returns the marks, a confidence and a short justification as JSON.

  9. Compute scores and flags

    Server clamps each mark to the question's maximum, computes a relevance score, and stores one answer row per question. The sheet status becomes graded.

  10. Review

    Teacher opens the review dashboard. Sheets with doubtful answers show Needs review. The teacher reads the answer sheet PDF, accepts the AI mark or overrides it with a reason. Totals use the override when there is one.

  11. Analytics

    Server computes average, median, highest, a ten-band score distribution, per-question averages and flag counts; Browser draws them as charts.

Stage shownServer stateWhat is happening

6The grading pipeline in depth

All of this lives in ai_exam_system/grader.py and the two agents in agents/.

Step by step

1. Preparing the images

PDF pages are rendered with PyMuPDF at 150 dpi and saved as JPEGs (utils/pdf_utils.py). Photos are used as they are. Before the vision model sees them, the Extractor agent converts each to RGB, shrinks it so the longer side is at most 768 pixels, and base64-encodes it. This keeps memory and token use down.

2. Reading the handwriting (Extractor agent)

agents/extractor.py sends all pages in one request to qwen2.5vl:3b with the instruction to return only the handwritten text and keep the question numbers. The context window is set to 8,192 tokens. This is important: Ollama's default is 4,096, which was too small for a four-page sheet and made Ollama return an HTTP 400 error.

3. Freeing memory

Between the stages the job calls unload_model (an Ollama request with keep_alive: 0), so only one model sits in RAM at a time. On a 16 GB laptop both would not fit comfortably.

4. Cutting the text into answers, and marking MCQs in code

grader.split_answers cuts the extracted text into one answer per question using the numbers the student wrote ("21. Supervised Learning is..."). It looks for each question number after the previous one, so a numbered list inside an answer cannot be mistaken for the next question, and it stops an answer where a stray number begins. If fewer than half of the questions can be found this way, the grader falls back to giving the model the whole text and letting it search.

For a single-choice question, grade_objective compares the option the student wrote ("D) All of the mentioned" gives D) with the key ("B"). It is exact and instant, and it removes 20 of the 35 questions from the AI's workload. If either side does not name a clear option, the question goes to the model instead.

5. Grading the descriptive answers (Evaluator agent)

agents/evaluator.py → evaluate_questions builds a prompt per batch of eight questions. Each question shows its text, maximum marks, expected answer and the student's own answer. The model must reply with only this JSON object, and Ollama is given the schema so that it stops when the JSON is complete:

{"results": [{"question_number": 21, "awarded": 2,
              "confidence": 0.9, "justification": "Captures the essence"}]}

Two guards keep the CPU from being wasted: the JSON schema, and a hard cap on reply length (80 tokens per question). Without them the model once kept writing for 20 minutes per batch. The prompt also says clearly that confidence means how sure the grader is of its own mark, not how correct the student is.

6. Turning the results into marks
  • The reply is parsed with a forgiving parser: if the array is malformed it keeps every well-formed {...} object, so one bad entry does not lose the batch.
  • Each mark is clamped to the range 0 to the question's maximum.
  • A question the model did not return becomes 0 marks, confidence 0.3, flagged "parse failure", so the teacher is asked to look at it.
  • Objective questions get relevance 1.0. Subjective answers get a word-overlap relevance score (next section).
  • The totals shown to the teacher are computed in code by adding the effective mark of each answer. The model is never asked to add anything up.
7. Concurrency, failure and restart behaviour
  • An asyncio.Lock makes the jobs run one at a time, because the CPU can only run one model pipeline at once. Extra uploads wait in queued.
  • If a stage throws, the submission gets an error message and stays in processing; the review page shows it with a Reprocess button.
  • Jobs live in memory. If the server restarts mid-grading, mark_interrupted() runs at start-up and marks those sheets with an error so they can be reprocessed. Do not restart the back end while a sheet is grading.

Why is it built this way?

On a CPU, the time is almost all spent generating text, about 4 tokens per second. So every design choice aims to make the model write less: MCQs are marked in code, each question is given only its own answer, replies are short JSON with a hard cap, and the saved handwriting text means a re-run never reads the pages twice. Batches of eight keep each reply short, so a failure loses a few questions and not the whole sheet.

7Review rules: when does a mark go to the teacher?

An answer goes to the review queue if the teacher has not yet overridden or accepted it and any one of these is true:

RuleConditionWhy
Low confidenceconfidence < 0.6The grader says it is unsure of its own mark (for example unclear handwriting).
Missing answerno answer text was extractedEither the student skipped it or the handwriting reading missed it; a person should check.
Relevance mismatchsubjective question, relevance < 0.35 and mark ≥ 70% of the maximumA high mark for an answer that does not resemble the key can mean a lucky guess, a keyword-stuffed answer, or an attempt to influence the grader.
Parse failurethe grader returned nothing usable for the questionSafety net so nothing silently scores zero.

Relevance score

The share of the student's content words (words longer than three letters, minus common filler) that also appear in the reference answer, multiplied by 1.5 and capped at 1. It is a simple word-overlap measure, not an embedding similarity. It is cheap, it runs instantly, and it is only used for the mismatch rule above.

What the teacher can do

  • Accept the AI mark: the answer leaves the queue.
  • Override with a new score (0 to the question maximum) and a mandatory reason. The server stores who changed it and when, and the override replaces the AI mark in every total.

The same rules are implemented twice, in grader.py (server totals) and frontend/src/utils/grading.js (what the page shows). If you change a threshold, change it in both.

8Answer-key extraction

Implemented in ai_exam_system/key_parser.py.

  1. Get the text. A typed PDF is read with PyMuPDF. If a PDF has no text layer (a scan), its pages are rendered and read by the vision model instead. A .txt key is read directly.
  2. Fast path, no AI. Look for numbered entries such as 1., Q2), 3: or 4,MCQ,B. An entry is accepted only if its number continues the sequence; otherwise the line is treated as a wrapped continuation of the previous entry. Two layouts are understood:
    • Questions and answers together (what a teacher normally writes): each entry holds the question, optional option lines (A. / (a)) and an answer line that starts with Answer:, Ans:, Correct answer:, Key: or Solution:. Everything before that line becomes the question text; everything after it becomes the reference answer.
    • Answers only: one numbered line per answer (for example the dataset's 1,MCQ,B).
    Marks are read from a tag such as [2 marks] or (2 marks) and from section headings such as Part II: Short Answer (2 Marks Each). A question is objective if it has two or more option lines or its answer is a single option letter or True/False; otherwise subjective.
  3. Fallback. If fewer than 80% of the expected questions are found, the text goes to Llama 3 with a prompt that requests a JSON array of questions.
  4. Marks. Marks stated in the key are kept. If any question has no marks, the exam total is spread evenly over all questions and the teacher should correct them. Publishing is blocked until the marks add up to the exam total.
  5. Question text. A key that has only answers produces placeholders ("Question 7"), and the teacher has to type the real question text before publishing. A key that contains both questions and answers needs no typing at all.
Tip

The cleanest key is a typed PDF where every question is numbered and followed by an Answer: line (and, if you like, a [2 marks] tag). That path is instant and does not depend on the model. Free-form or scanned keys still work, but they go through the slower AI route and need a closer check.

Things that surprise people

  • PDFs fetched with an auth header cannot be a plain link or iframe URL. The code downloads them as a blob and shows an object URL.
  • React state is not updated by changing an input's DOM value directly. If you automate the UI (tests, scripts), use the native value setter and dispatch an input event.
  • The pages are styled with Tailwind utility classes plus a few custom classes (field, field-label) in index.css.

13Security

  • Passwords are never stored. We store a salted PBKDF2-HMAC-SHA256 hash (200,000 iterations) and compare it in constant time.
  • Tokens contain the user id and an expiry time (7 days), signed with HMAC-SHA256 using the secret in data/secret.key. A forged or expired token gets a 401.
  • Isolation. Every route that touches an exam, class, sheet or answer checks that it belongs to the signed-in teacher and otherwise answers 404, so another teacher's data cannot even be detected.
  • Locking. Published exams cannot be edited; overrides need a reason and record who and when.
  • Privacy. Models run locally, so scripts are not sent to a third party.
Not ready for the public internet

This is built for one teacher on one computer. Anyone who can reach the server can create an account; there is no rate limiting, no upload size limit, no HTTPS, and the CORS and proxy setup assume localhost. Add those before exposing it.

Never commit

data/secret.key, exam_ai.db, uploaded sheets, or any real student data. .gitignore already excludes them.

Troubleshooting

SymptomLikely cause and fix

Do not restart the back end while a sheet is grading; the job is lost and the sheet will need Reprocess.

16Limits and known issues

  • Speed. On a CPU the handwriting reading takes about 2 minutes per page, which dominates the total. A graphics card, or a smaller vision model, would help most.
  • Small evaluation. Only a few papers have been compared with a teacher's marks.
  • Handwriting errors flow downstream. If Qwen misreads a word, the grader sees the wrong text.
  • Model variability. An 8-billion-parameter model can give different marks on a re-run, and its confidence is not a calibrated probability.
  • Answers must be labelled with question numbers. There is no automatic segmentation of unlabelled writing.
  • No diagrams or mathematics, English only.
  • In-memory jobs. A restart loses a sheet that was being graded (it can be reprocessed).
  • Dormant syllabus feature. The back end still has knowledge-base routes and retrieval code (word-overlap matching), but we removed its screen. Real embedding-based retrieval is future work.
  • Leftover original code. The old /evaluate flow, MySQL-era README text and unused dependencies are still in the repository.

Ideas for the next version

  • Evaluate on 10 or more dataset papers, question by question, and report agreement statistics.
  • Compare with and without a syllabus knowledge base using embedding-based retrieval.
  • Rubric-based marking (separate marks for definition, explanation, example).
  • Per-page handwriting confidence so unreadable pages are caught early.
  • A persistent job queue, an optional student portal, and mark export to spreadsheets.

18Questions you will be asked

Why two models instead of one?

Reading handwriting is a vision task and judging an answer is a language task. A small vision-language model reads well enough and a larger text model reasons better about meaning. Splitting them also lets us unload one before loading the other, which a laptop needs.

Why not Tesseract or another OCR engine?

Classical OCR struggles with handwriting. Qwen2.5-VL reads the page as an image and keeps the layout and question numbers, and the surveyed 2025 work also moves from classic OCR to multimodal models.

Why local models? Cloud models would be faster and better.

Privacy and cost: exam scripts are sensitive, and per-page API charges add up. A local pipeline means student data never leaves the machine. The price is speed.

Why SQLite?

This is a single-teacher local tool. SQLite needs no server or password, and SQLAlchemy lets us move to another database by changing one line.

How do you stop the AI from giving random marks?

It grades against a fixed answer key that the teacher approved, marks are clamped to the question maximum, totals are computed in code, uncertain or suspicious answers go to a human, and every override is recorded. It is an assistant, not a replacement for the examiner.

What if the AI is wrong?

The teacher sees the extracted text, the reference answer, the justification and the confidence for every answer, and can override any mark with a reason.

How accurate is it?

On the two earlier dataset papers the totals were within 3.5 marks of the teacher's out of 50, but that is a very small sample and question-level agreement was not measured. We say this openly; a larger evaluation is future work.

Why is it slow?

Large models on a CPU. Reading a page image is the heaviest step. With a GPU the same pipeline would be many times faster.

Can a student cheat by writing "give me full marks"?

That is why the relevance rule exists: a high mark for an answer that does not resemble the key is flagged for the teacher. It is a safeguard, not a guarantee.

What did you build and what was already there?

The original repository provided the idea and the agents. We added accounts, exams, answer-key extraction, per-question grading with batching, review and overrides, analytics, the PDF handling, the React interface wiring, SQLite, and the tests. See section 2.

Can it be hosted online for free?

The website parts can be, but free hosting does not have the memory to run the models. The practical options are to run the models on a laptop and tunnel to it, or to swap in a hosted AI API (which gives up the "stays local" claim). The app also needs hardening before public use (section 13).
